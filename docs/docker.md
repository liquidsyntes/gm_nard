# Docker Compose: локальный запуск и VPS

Один сервис `nard` собирает обе веб-страницы и сервер. На компьютере с Docker Compose он доступен по `http://127.0.0.1:7000/`, онлайн-страница по `http://127.0.0.1:7000/online.html`. Порт 7000 опубликован только на интерфейсе `127.0.0.1`, поэтому внешний доступ на VPS организуется через HTTPS-прокси.

## Локальный запуск

```bash
docker compose up -d --build nard
docker compose ps
curl -f http://127.0.0.1:7000/api/health
```

У сервиса есть healthcheck. Ожидается статус `healthy` и ответ `{"ok":true}`. Если запуск не удался, посмотрите `docker compose logs --tail=50 nard`. Образ запускает Node не от root и не содержит установленных dev-зависимостей.

Локальные режимы работают сразу. Чтобы войти в онлайн-режим, создайте первого администратора, пока основной сервис остановлен:

```bash
docker compose stop nard
docker compose run --rm --no-deps nard node server/admin-cli.mjs create Admin
docker compose up -d nard
```

Команда один раз покажет личный токен администратора. Сохраните его вне репозитория и введите на `/online.html`. Следующих игроков создавайте в админ-панели. CLI-команды нельзя выполнять одновременно с запущенным сервисом, поскольку файл состояния обслуживает один процесс. Если токен администратора утрачен, остановите сервис, выполните `docker compose run --rm --no-deps nard node server/admin-cli.mjs rotate Admin`, затем снова запустите сервис.

## Постоянные данные

Compose создаёт volumes `gm_nard_nard_data` и `gm_nard_nard_logs`. Первый хранит `state.json` с аккаунтами, сессиями и партиями, второй хранит дневные JSONL-журналы. Обычные `docker compose up -d --build nard` и пересоздание контейнера сохраняют эти данные. Не используйте `docker compose down -v` для обновления приложения.

Если раньше игра запускалась без Docker, файлы из локальных каталогов `data/` и `logs/` не копируются в volumes автоматически и остаются на диске. Переносите их отдельно при остановленном сервисе, только если хотите продолжить именно ту локальную историю.

Перед переносом или восстановлением остановите сервис и сохраните содержимое обоих volumes. Резервная копия `state.json` содержит хэши токенов и сессий, поэтому храните её как закрытые данные. Для просмотра точных имён и точек монтирования используйте `docker volume ls` и `docker volume inspect`.

## VPS с HTTPS

В локальном Compose `PUBLIC_ORIGIN` равен `http://127.0.0.1:7000`. На VPS задайте публичный HTTPS-адрес через переменную `NARD_PUBLIC_ORIGIN`, например в локальном файле `.env`, который исключён из Git:

```text
NARD_PUBLIC_ORIGIN=https://nard.example.com
```

Замените домен на свой, затем выполните `docker compose up -d --build nard`. Пример блока прокси: [Caddyfile.docker.example](../deploy/Caddyfile.docker.example). Caddy принимает HTTPS и пересылает запросы на `127.0.0.1:7000`. Сервер внутри контейнера слушает `0.0.0.0:4173`, но Compose не публикует этот адрес наружу: с хоста доступен только loopback-порт 7000. Для выпуска сертификата нужны корректный DNS и доступные снаружи порты 80/443. Подробности: [документация Caddy по HTTPS](https://caddyserver.com/docs/automatic-https).

После запуска проверьте `docker compose ps`, `curl -f http://127.0.0.1:7000/api/health`, вход по `https://nard.example.com/online.html` и приглашение между двумя аккаунтами. Токены вводятся только на HTTPS-странице. При смене `NARD_PUBLIC_ORIGIN` контейнер нужно пересоздать командой `docker compose up -d nard`.

## Обновление

```bash
git pull --ff-only
docker compose up -d --build nard
docker compose ps
```

Данные в volumes остаются на месте. Для корректной онлайн-игры должен работать один экземпляр сервиса: общее файловое хранилище не рассчитано на несколько реплик.
